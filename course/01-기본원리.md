## 1.1 하네스란? — 에이전트(누가) vs 스킬(어떻게)

**하네스(Harness)** = 특정 도메인의 일을 처리하도록 설계된 **에이전트 팀 + 스킬 + 오케스트레이터**의 묶음.

핵심은 두 가지를 분리하는 것입니다:

| 개념 | 질문 | 예시 |
|------|------|------|
| **에이전트(Agent)** | **누가** 하는가 | "경매 데이터 수집가" |
| **스킬(Skill)** | **어떻게** 하는가 | "법원경매를 수집하는 법" |

**왜 분리하나?**
- 같은 스킬을 여러 에이전트가 공유할 수 있다
- 에이전트를 파일로 남기면 **다음에도 재사용**된다
- "누가"와 "어떻게"를 나누면 각각 독립적으로 개선할 수 있다

> 💡 비유: 에이전트는 "직원", 스킬은 "업무 매뉴얼". 직원이 바뀌어도 매뉴얼은 남고, 매뉴얼 하나를 여러 직원이 쓴다.

> 📌 **수강생이 할 일**: 이 파일들을 손으로 만들지 않습니다. Part 2에서 `/harness`를 트리거하면 Claude가 생성합니다. 여러분은 **구조를 이해하고 검토·조정**만 하면 됩니다.

---

## 1.2 실행 모드: 에이전트 팀 vs 서브에이전트

에이전트를 여럿 쓰는 방법은 두 가지입니다.

**에이전트 팀 (기본값)** — 팀원끼리 직접 메시지를 주고받고 공유 작업목록으로 자체 조율. 발견을 공유하고 상충을 토론 → **품질이 높아진다**. 2명 이상 실시간 협업할 때.

**서브에이전트 (대안)** — 각자 독립적으로 일하고 결과만 반환. 병렬 실행. 팀 통신이 불필요할 때.

> 📌 판단 기준: 팀원끼리 중간 산출물을 서로 참조하며 조율해야 하면 **팀**, 각자 독립적으로 일하고 결과만 모으면 **서브에이전트**.

우리 프로젝트는 수집 3인을 **병렬 서브에이전트(팬아웃)** 로 돌리고, 통합·검증은 순차로 잇는 하이브리드입니다.

## 1.3 스킬 설계: 트리거 description과 단계적 로딩

### description은 트리거의 전부다
스킬은 상단 `description` **하나로만** 발동됩니다. Claude는 트리거를 **보수적으로** 판단하므로, description을 **적극적으로(pushy)** 써야 합니다.

- ❌ "경매 데이터를 처리하는 스킬" → 언제 써야 할지 모호
- ✅ "경매물건 수집. …'경매 레이어 만들어줘', '경매물건 수집' 요청 시 사용." → 하는 일 + 트리거 상황

### 본문은 "Why"를 설명하라
"하지 마라" 같은 지시보다 **이유**를 설명하면 Claude가 엣지 케이스에서도 올바르게 판단합니다.
- ❌ "UI 페이지 버튼을 클릭하지 마라"
- ✅ "UI 클릭은 물건을 대량 누락시킨다(328건 중 113건만 잡힌 사례). API 페이징은 결정적이다."

<details>
<summary>🔍 심화 — 스킬의 단계적 정보 공개(Progressive Disclosure)</summary>

컨텍스트 윈도우는 공공재입니다. 스킬은 3단계로 로딩됩니다:

| 단계 | 로딩 시점 | 크기 목표 |
|------|----------|----------|
| Metadata (name+description) | 항상 | ~100단어 |
| SKILL.md 본문 | 트리거 시 | <500줄 |
| references/ | 필요할 때만 | 무제한 |

상세한 데이터 규격·도메인별 변형은 `references/`로 빼고, 본문엔 "언제 그 파일을 읽어라"는 포인터만 남깁니다. 이 관리는 `/harness`가 대신 해줍니다.
</details>

## 1.4 공유 데이터 계약: 표준 GeoJSON은 왜 필요한가

우리 지도엔 5종 레이어가 올라갑니다. 각 수집가가 **제멋대로 형식**으로 데이터를 만들면, 통합 담당은 레이어마다 특수 처리를 해야 하고 레이어가 늘 때마다 렌더러를 고쳐야 합니다.

**해결책: 모든 레이어가 따르는 표준 규격(계약)을 하나 정한다.**

규칙 3가지만 기억하세요:
1. 좌표계는 **WGS84 고정**, 순서는 `[경도, 위도]`
2. 모든 항목에 **필수 5필드**(layer / id / name / category / color)
3. 빈 레이어도 허용 (`count: 0`) — 수집 실패가 전체를 막지 않게

> 💡 이 계약 덕분에 렌더러는 `category`와 `color`만 믿으면 되고, **새 레이어를 코드 수정 없이 추가**할 수 있습니다. 이게 좋은 설계의 힘입니다.

<details>
<summary>🔍 심화 — 실제 표준 GeoJSON 형태 (에이전트가 이 규격으로 산출)</summary>

```json
{
  "type": "FeatureCollection",
  "meta": { "layer": "auction", "count": 9759, "source": "..." },
  "features": [{
    "type": "Feature",
    "geometry": { "type": "Point", "coordinates": [127.1, 37.4] },
    "properties": {
      "layer": "auction", "id": "...", "name": "...",
      "category": "...", "color": "#20c997"
    }
  }]
}
```
전체 규격은 `/harness`가 `.claude/skills/realestate-map-build/references/geojson-schema.md`에 만들어 둡니다. 수강생이 직접 작성할 필요 없습니다.
</details>

## 1.5 오케스트레이터: 팬아웃·팬인·파이프라인

**오케스트레이터**는 "누가 언제 어떤 순서로 협업하는가"를 정의합니다. 우리 프로젝트의 데이터 흐름:

```
        ┌─ auction-collector (경매) ──┐
[시작] ─┼─ zone-specialist (구역) ────┼─→ map-integrator ─→ qa-validator ─→ [지도]
        └─ poi-collector (인프라) ────┘   (통합·렌더)      (검증)
         └──── 팬아웃 (병렬) ────┘      └─── 팬인 (순차) ───┘
```

- **팬아웃**: 독립 작업을 병렬로 흩뿌린다 → 빠르다
- **팬인**: 결과를 통합 담당 한 곳으로 모은다
- **파이프라인**: 통합 → 검증은 순서 의존

> 📌 여러분은 이 흐름을 직접 코딩하지 않습니다. 오케스트레이터 스킬 하나를 트리거하면 Claude가 순서대로 팀을 가동합니다.
