## 5.1 배운 원리 회고

이 강의에서 만든 것은 지도지만, 진짜 자산은 **재사용 가능한 사고 프레임**입니다.

### 핵심 원리 5가지

1. **에이전트(누가) ↔ 스킬(어떻게) 분리**
   → 직원과 매뉴얼을 나누면 각각 재사용·개선된다

2. **소스 성격으로 에이전트를 묶는다**
   → 5레이어를 4수집단위로. 같은 기법이면 한 명에게.

3. **표준 데이터 계약이 확장성을 만든다**
   → 렌더러가 `category`·`color`만 믿으면, 새 레이어를 코드 수정 없이 추가

4. **팬아웃 병렬 수집 → 팬인 통합 → 독립 QA**
   → 빠르고, 검증되고, 부분 재실행 가능

5. **정직한 엔지니어링**
   → 없는 데이터는 억지로 만들지 않고 사유 기록. null·빈 레이어를 방어적으로 처리. push 전 민감정보 확인.

### 우리가 실제로 잡은 함정들
| 함정 | 교훈 |
|------|------|
| 지도가 마커 없이 베이스만 표시 | null geometry 가드 필수, QA는 경계면 교차 비교 |
| Excel 좌표가 정수 반올림 | 좌표계(KATEC/TM128)를 검증하고 재투영 |
| 자치구명이 코드와 불일치 | 속성 맹신 금지, 권위 코드로 재매핑 |
| 홈 디렉토리가 Git 저장소 | push 전 저장소·민감정보 확인 |
| 정비구역 데이터 없음 | "없음" vs "미확보" 구분, 사유 기록 |

## 5.2 다른 도메인에 응용하기

같은 하네스 패턴을 다른 프로젝트에 옮겨봅시다. **구조는 그대로, 도메인만 바뀝니다.**

### 예시 A: 논문 리서치 어시스턴트
```
수집가(팬아웃): arxiv-collector · citation-collector · dataset-collector
통합가(팬인):   review-synthesizer (표준 논문 스키마로 병합)
검증가:         fact-checker (인용 정합성 교차검증)
계약:           표준 Paper JSON (title/authors/abstract/citations)
```

### 예시 B: 이커머스 경쟁사 분석
```
수집가: price-scraper · review-scraper · spec-scraper
통합가: product-comparator (표준 Product 스키마)
검증가: data-qa (가격 이상치·매핑 검증)
```

### 응용 체크리스트
- [ ] 이 도메인의 **데이터 소스**는 몇 종류인가? → 소스 성격으로 수집가를 묶어라
- [ ] 모든 산출물이 따를 **표준 계약(스키마)** 은 무엇인가?
- [ ] 무엇을 **QA로 교차검증**해야 하는가?
- [ ] 어떤 **후속 요청**이 올까? → 오케스트레이터 description에 후속 키워드 포함

> 💡 새 도메인이면 Claude Code에서 `/harness` 스킬을 트리거하고 "○○ 도메인 하네스 구성해줘"라고 하면, 이 강의에서 배운 과정을 대화로 안내받을 수 있습니다.
