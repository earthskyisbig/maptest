데이터 수집·좌표 변환·렌더링 코드는 에이전트가 알아서 처리합니다. 여러분이 직접 짤 필요가 없습니다. 그래서 각 단계는 이 흐름을 따릅니다:

구현 코드(파이썬·JS·git)는 › 심화 접이식 상자에 넣어 뒀습니다. 궁금한 사람만 펼쳐 보면 되고, 안 봐도 실습에 지장 없습니다.

Part 00

오리엔테이션 — 왜 "한 대"가 아니라 "팀"인가

초보자는 보통 이렇게 시작합니다: "경매물건이랑 정비구역이랑 다 모아서 지도 만들어줘." 이 한 방 방식은 곧 무너집니다.

한 대에게 다 시키면에이전트 팀으로 나누면
컨텍스트 폭발 — 크롤·GIS·렌더가 뒤섞여 길을 잃음전문가별로 분리돼 각자 집중
순차 진행 — 하나 끝나야 다음병렬 수집으로 빠름
재사용 불가 — 매번 처음부터 설명파일로 정의돼 다음에도 재사용
검증 부재 — 누가 결과를 검사?독립 QA가 교차검증

이 "에이전트 팀 + 스킬 + 오케스트레이터" 묶음을 하네스(Harness)라 부릅니다. 이 강의의 뼈대입니다.

Part 01

기본 원리 — 5가지 개념

코드를 외울 필요는 없습니다. 이 개념만 잡으면 이후 모든 선택이 "왜 그런지" 납득됩니다.

1 · 에이전트(누가) ↔ 스킬(어떻게)

에이전트는 "누가 하는가"(경매 수집가), 스킬은 "어떻게 하는가"(경매를 수집하는 법). 직원과 업무 매뉴얼처럼 분리하면 각각 재사용·개선됩니다.

2 · 에이전트 팀 vs 서브에이전트

팀원끼리 조율이 필요하면 팀, 각자 독립적으로 일하고 결과만 모으면 서브에이전트(병렬). 우리는 수집 3인을 병렬로 흩뿌립니다.

3 · 스킬 트리거는 description이 전부

스킬은 description 하나로 발동됩니다. "경매 레이어 만들어줘" 같은 실제 사용자 표현을 넣어야 트리거됩니다. 그리고 규칙보다 "왜"를 설명해야 엣지 케이스에서도 옳게 판단합니다.

4 · 표준 데이터 계약 — 확장성의 열쇠

5종 레이어가 제각각 형식이면 렌더러를 매번 고쳐야 합니다. 모든 레이어가 따르는 표준 GeoJSON 규격을 하나 정하면, 렌더러는 category·color만 믿으면 되고 새 레이어를 코드 수정 없이 추가할 수 있습니다.

규칙 3가지만 기억 ① 좌표계 WGS84 고정 · ② 필수 5필드(layer/id/name/category/color) · ③ 빈 레이어도 허용(수집 실패가 전체를 막지 않게)
› 심화 — 실제 표준 GeoJSON 형태
{
  "type": "FeatureCollection",
  "meta": { "layer": "auction", "count": 9759 },
  "features": [{
    "geometry": { "type": "Point", "coordinates": [127.1, 37.4] },
    "properties": {
      "layer": "auction", "id": "...", "name": "...",
      "category": "...", "color": "#20c997"
    }
  }]
}

이 규격은 /harness가 references/geojson-schema.md에 자동 생성합니다.

5 · 오케스트레이터 — 팬아웃·팬인

독립 작업을 병렬로 흩뿌리고(팬아웃), 결과를 통합 담당 한 곳으로 모읍니다(팬인). 통합→검증은 순서 의존 파이프라인. 여러분은 이 흐름을 코딩하지 않고, 오케스트레이터 하나를 트리거합니다.

Part 02

하네스 구축 — 설계하고, 생성시키고, 검토한다

파일을 손으로 짜지 않습니다. /harness를 트리거하고 도메인을 설명하면 Claude가 에이전트 5종·스킬 5종·데이터 계약을 생성합니다. 여러분의 일은 어떻게 나눌지 설계 + 생성물 검토입니다.

여러분의 핵심 판단 — 5레이어를 몇 명에게?

레이어가 5개라고 5명을 만들면 과합니다. 데이터 소스 성격으로 묶습니다.

레이어소스 성격담당 에이전트
경매물건법원경매 크롤 + 지오코딩auction-collector
정비·공공주택·산단GIS 경계 — 기법 동일zone-layer-specialist
생활인프라Overpass POIpoi-collector
통합·렌더표준 병합 → 지도map-integrator
검증좌표·스키마·정합qa-validator
핵심 통찰 정비·공공주택·산단은 셋 다 "면 경계를 공공 GIS에서 가져온다"는 점이 같습니다. 기법이 같으면 한 명으로 묶어 조율 비용을 줄입니다 → "5레이어 → 4수집단위".
입력
/harness 부동산 전용 맵서비스를 만들 거야. 경매물건, 정비구역, 공공주택, 산업단지, 생활인프라를 한 지도에 레이어로 보여주고 싶어.

🤖 에이전트가 하는 일: 기존 하네스 감사 → 에이전트 분리안 제시 → 확인 후 .claude/agents/ 5종, .claude/skills/ 5종, 데이터 계약, CLAUDE.md를 자동 생성.

🧠 여러분의 판단: 분리안에 동의하거나("그대로 진행"), 조정을 요청("정비구역은 따로 빼줘").

생성된 것 검토 체크

  • 에이전트 정의에 핵심 역할·작업 원칙("왜" 포함)·팀 통신이 있는가
  • 스킬 description에 실제 사용자 표현("만들어줘/수집/갱신")이 있는가
  • 오케스트레이터에 후속 키워드("다시/재실행/추가")가 있는가 — 없으면 후속 요청이 트리거 안 됨
  • .claude/commands/는 비어있는가 (커맨드는 만들지 않음)
› 심화 — 실제 에이전트 정의 파일 골격

## 핵심 역할
법원경매 물건을 수집·지오코딩하여 표준 GeoJSON으로 산출.

## 작업 원칙
- 목록수집은 API 직접 페이징 (UI 클릭은 대량 누락)
- 좌표가 데이터의 생명 — 실패 물건은 버리지 말고 실패율 리포트

## 팀 통신
- 발신: map-integrator에게 파일 경로, qa-validator에게 실패율
Part 03

팀 가동 — 한 문장이면 된다

입력
분당구 경매물건 + 정비구역 + 지하철 지도 만들어줘

🤖 에이전트: 오케스트레이터가 수집 3인을 병렬로 흩뿌립니다. 셋이 동시에 일하므로 빠릅니다.

에이전트결과 (실제 기록)특이점
인프라 수집379 POI (학교154·병원108·마트97·지하철20)서버 혼잡 → 대체 서버로 성공
경매 수집64건 (62 지도 표시)좌표 형식 문제를 스스로 발견·해결
구역 수집공공주택 13, 정비구역 0, 산단 0빈 레이어를 사유와 함께 정직하게 반환
🧠 여러분의 판단 결과 숫자가 상식적인가? 실패·빈 레이어의 사유가 납득되는가? — 좋은 에이전트는 억지로 지어내지 않고 사유를 남깁니다.

QA 검증 — 결과가 "정말" 맞는지 ★

이 강의의 하이라이트. 지도를 열었더니 베이스 지도만 보이고 마커·폴리곤이 하나도 안 나왔습니다.

QA 에이전트가 한 일: "파일이 있나"가 아니라 데이터가 제공하는 것과 렌더러가 기대하는 것을 대조했습니다. 근본 원인: 경매 64건 중 2건이 좌표 없는 물건인데 렌더러가 방어하지 못해 스크립트 전체가 중단 → 아무것도 안 보인 것. 에이전트가 데이터에서 2건을 빼고(64→62) 방어 가드를 추가해 해결.

수강생 교훈 에이전트가 결과를 내도 독립 QA를 두면 치명적 버그를 잡습니다. "그럴듯한 결과"를 그냥 믿지 마세요.
› 심화 — 실제 버그와 수정 코드
(AUCTION.features||[]).forEach(function(f){
  // geometry가 null이면 예외 → 스크립트 전체 중단
  if(!f.geometry||!f.geometry.coordinates) return;  // ← 방어 가드
  var c = f.geometry.coordinates;
});

교훈: 데이터 계약에 "좌표 필수"가 있어도 렌더러는 방어적으로 짜야 하고, QA는 각 모듈 완성 직후 점진적으로 돌려야 일찍 잡습니다.

Part 04

반복 개선 — 피드백을 주면 진화한다

하네스는 한 번 만들고 끝이 아닙니다. 여러분이 짧게 요청하면 에이전트가 고칩니다. 여기서 배우는 건 "무엇을 어떻게 요청하는가"입니다.

부분 개선 — 담당만 재작업

입력
카카오맵으로 보여주고, 마커 색이 지도 배경과 구분이 잘 안돼

전체를 다시 안 돌리고 렌더 담당만 재작업 → 카카오맵 전환 + 핀형 흰 외곽선 마커. 부분 요청이 빠릅니다.

확장 — 데이터 먼저, 화면 나중

입력
분당구만 했는데 서울 포함 수도권이 나오게 하고, 지역을 선택할 수 있게 해줘

① 경매 수집가가 서울+수도권 전체로 확장 + 지역 태그(시도·시군구) 부착 → 9,759건. ② 렌더 담당이 그 태그로 지역 드롭다운을 생성.

핵심 감각 지역 선택 같은 UI는 데이터에 태그가 있어야 가능합니다. "UI 먼저"가 아니라 "수집(데이터) 먼저, 렌더(화면) 나중".

데이터가 없을 때 — 정직하게 ★

처음 분당구 정비구역은 공개 데이터에 없었습니다. 에이전트는 억지로 지어내지 않고 0건으로 두되, 왜 없는지(2026.4 지정됐으나 미반영)와 시도한 4개 소스의 실패 사유를 기록했습니다. 지도엔 "데이터 없음"이 아니라 "경계 미확보 ⓘ"로 표시.

반전: 서울로 확장하자 "서울 전용이라 못 쓰던" 데이터가 유효해져 → 서울 25개 자치구 2,585건 확보.

세 가지 교훈 ① 없으면 억지로 만들지 말고 사유 기록(환각 방지) · ② "없음"과 "미확보"는 다르다 · ③ 스코프가 바뀌면 못 쓰던 데이터가 유효해진다

저장 — 안전은 에이전트가 점검

입력
github 내 저장소로 커밋하고 푸시해줘

실제로 홈 폴더 전체가 저장소여서 .ssh·.env 같은 민감정보가 유출될 뻔했습니다. 에이전트가 이를 발견하고 프로젝트 폴더만 분리해 안전하게 올렸습니다. git을 몰라도 "안전하게 올려줘"면 이런 위험을 점검합니다.

Part 05

마무리 — 지도는 시작일 뿐

이 강의에서 만든 건 지도지만, 진짜 자산은 재사용 가능한 사고 프레임입니다. 같은 구조로 도메인만 바꾸면 됩니다.

도메인수집(팬아웃)통합·검증
논문 리서치arxiv · citation · datasetsynthesizer + fact-checker
이커머스 분석price · review · speccomparator + data-qa
부동산 맵(본 강의)auction · zone · poiintegrator + qa

응용 체크리스트

  • 이 도메인의 데이터 소스는 몇 종류? → 성격으로 수집가를 묶어라
  • 모든 산출물이 따를 표준 계약(스키마)은 무엇인가?
  • 무엇을 QA로 교차검증해야 하는가?
  • 어떤 후속 요청이 올까? → 오케스트레이터 description에 반영
다음 도전 실거래가 레이어를 새로 추가해 보세요 — 표준 계약만 지키면 렌더러 수정 없이 지도에 붙습니다. 그것이 좋은 설계의 힘입니다.
