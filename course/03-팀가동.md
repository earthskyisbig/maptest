# Part 3. 팀 가동 — 실제 지도 산출

> 하네스가 준비됐으니 실제 데이터로 지도를 만듭니다. 여러분은 **한 문장을 입력**하고, 에이전트 팀이 알아서 수집·통합·검증합니다. 여러분의 일은 **결과를 읽고 판단하는 것**입니다.

## 🎯 학습목표
- 한 문장으로 팀 전체를 가동한다
- 에이전트가 낸 결과를 읽고 품질을 판단한다
- QA가 버그를 잡는 과정을 이해한다

---

## 3.1 ⌨️ 따라하기: 팀 가동은 한 문장

```
분당구 경매물건 + 정비구역 + 지하철 지도 만들어줘
```

### 에이전트가 하는 일 (여러분은 지켜봅니다)
오케스트레이터가 `_workspace/`가 없음을 확인하고, 수집 3인을 **병렬로** 흩뿌립니다. 셋이 동시에 일하므로 빠릅니다.

### 여러분이 보게 되는 결과 (실제 기록)

| 에이전트 | 결과 | 특이점 |
|----------|------|--------|
| 인프라 수집 | 379개 POI (학교154·병원108·마트97·지하철20) | Overpass 서버 혼잡 → 대체 서버로 성공 |
| 경매 수집 | 64건 (62개 지도 표시) | 좌표 형식 문제를 스스로 발견·해결 |
| 구역 수집 | 공공주택 13지구, 정비구역 0, 산단 0 | 빈 레이어를 사유와 함께 정직하게 반환 |

### 여러분이 내리는 판단
- 결과 숫자가 상식적인가? (분당구에 경매 64건 — 합리적)
- 실패·빈 레이어의 **사유가 납득되는가**?

> 💡 **배울 점**: 경매 수집가는 좌표가 이상하다는 걸 스스로 발견하고 고쳤고, 구역 수집가는 정비구역 데이터가 없자 **억지로 만들지 않고** 사유를 남겼습니다. 좋은 에이전트는 이렇게 판단합니다. 여러분은 그 판단이 타당한지만 확인하면 됩니다.

<details>
<summary>🔍 심화 — 경매 수집가가 내부적으로 해결한 것</summary>

Excel의 위경도 컬럼이 정수로 반올림돼(127, 37) 못 쓰는 상태였습니다. 수집가는 다른 좌표 컬럼이 **KATEC(TM128) 좌표계**임을 실제 위치와 대조해 검증하고, `pyproj`로 WGS84로 재투영했습니다. 지오코딩 API 없이 정확한 좌표를 얻은 것. — 이 모든 걸 에이전트가 자동 처리했고, 여러분은 결과(62/64 배치)만 받습니다.
</details>

## 3.2 통합 렌더링 — 자동으로 이어짐

수집 3인이 끝나면 `map-integrator`가 5개 레이어를 하나의 HTML로 병합합니다. **여러분이 따로 시킬 필요 없이** 오케스트레이터가 순서대로 진행합니다.

### 📖 왜 매끄럽게 합쳐지나
통합가는 각 레이어의 특수 사정을 몰라도 됩니다. **표준 계약의 `category`·`color`만 믿고** 렌더합니다. 빈 레이어(정비/산단)는 "데이터 없음"으로 표시하고 넘어갑니다. → 이것이 Part 1.4 데이터 계약의 보상입니다.

결과: `estate_map.html` 한 파일 (경매 클러스터 + 공공주택 폴리곤 + 인프라 토글).

## 3.3 QA 검증 — 결과가 "정말" 맞는지 ⭐

> 이 파트가 하이라이트입니다. **실제로 지도가 깨졌고, QA 에이전트가 잡았습니다.** 수강생은 이 과정을 통해 "결과를 믿기 전에 검증한다"를 배웁니다.

### 증상
지도를 열었더니 **베이스 지도만 보이고 마커·폴리곤이 하나도 안 나왔습니다.**

### QA 에이전트가 한 일
qa-validator는 "파일이 있나"만 보지 않고, **데이터가 제공하는 것과 렌더러가 기대하는 것을 대조**했습니다. 그 결과 근본 원인을 지목:

> 경매 64건 중 **2건이 좌표가 없는 물건**("자동차")이었고, 렌더러가 이걸 방어하지 못해 **스크립트 전체가 중단** → 그래서 아무것도 안 보였다.

### 자동으로 수정됨
에이전트가 (1) 데이터에서 좌표 없는 2건을 빼고(64→62), (2) 렌더러에 방어 가드를 추가했습니다. 여러분은 브라우저를 새로고침해 **마커가 보이는지 확인**만 하면 됩니다.

<details>
<summary>🔍 심화 — 실제 버그와 수정 코드</summary>

```javascript
// 문제: geometry가 null이면 예외 → 스크립트 전체 중단
(AUCTION.features||[]).forEach(function(f){
  var c=f.geometry.coordinates;   // ← null이면 크래시
});

// 수정: 방어 가드 추가
(AUCTION.features||[]).forEach(function(f){
  if(!f.geometry||!f.geometry.coordinates) return;  // ← 가드
  var c=f.geometry.coordinates;
});
```
교훈: 데이터 계약에 "좌표 필수"가 있어도 렌더러는 방어적으로 짜야 하고, QA는 각 모듈 완성 직후 **점진적으로** 돌려야 이런 걸 일찍 잡습니다.
</details>

> 💡 **수강생 관점 교훈**: 에이전트가 결과를 내도 **QA라는 독립 검증자**를 두면 이런 치명적 버그를 잡습니다. "그럴듯해 보이는 결과"를 그냥 믿지 마세요.

---

## 3.4 브라우저에서 확인

에이전트가 지도 파일을 기본 브라우저로 열어줍니다. 화면에:
- 경매물건 마커 (클러스터)
- 공공주택 폴리곤
- 레이어 토글 패널 + 범례

가 정상 표시되면 성공입니다.

### ⚠️ 흔한 실수 (여러분이 겪을 수 있는 것)
- **빈 레이어 때문에 전체가 안 뜬다** → 방금 배운 QA·가드로 해결됨
- **카카오맵이 안 뜬다** → Part 4에서 카카오 키 처리를 다룹니다

---

## 정리: 이 파트에서 배운 것
1. 팀 가동은 **한 문장**이면 된다 (오케스트레이터가 순서를 관리)
2. 여러분의 일은 **결과 숫자·사유가 타당한지 판단**하는 것
3. **QA 독립 검증**이 치명적 버그를 잡는다 — 결과를 그냥 믿지 말라
4. 빈 데이터·실패를 **정직하게** 다루는 에이전트가 좋은 에이전트
